# ADR-004: Schema Consistency Analysis Strategy

**Status**: Accepted  
**Date**: 2026-05-27  
**Deciders**: Engineering Lead, Data Science Lead  
**Technical Story**: [PRD-002 §5.3](../../plans/PRD-002-preflight-integration-tester.md)

---

## Context and Problem Statement

Preflight's core diagnostic value is detecting how the same real-world business entity — a *Customer*, an *Order*, a *Product* — is represented inconsistently across connected enterprise systems. A customer in Salesforce CRM might be called `Account` with a field `AccountId`, while the same entity in SAP ERP is `KNA1` with field `KUNNR`, and in the data warehouse it is `dim_customer` with `customer_uuid`.

The schema analysis engine must:

1. **Automatically discover** how entities are represented in each system without requiring manual mapping configuration.
2. **Match** corresponding entities and fields across systems despite naming differences, type differences, and structural differences.
3. **Rank** detected inconsistencies by their likely impact on the proposed AI deployment.
4. **Handle uncertainty**: not every match is certain; the engine must express confidence levels rather than binary yes/no decisions.
5. **Scale**: an enterprise may have hundreds of entity types and tens of thousands of fields across all connected systems.

The challenge is that enterprise systems were designed independently; there is no canonical cross-system ontology to anchor mapping to.

---

## Decision Drivers

- Accuracy: false negatives (missed inconsistencies) are worse than false positives (flagging non-issues)
- Automation: manual mapping tables are not viable at enterprise scale
- Confidence expression: output must convey uncertainty, not false precision
- Explainability: buyers and architects need to understand *why* a match was identified
- Configurability: matching thresholds must be tunable without code changes
- Performance: schema analysis should complete in minutes, not hours

---

## Considered Options

### Option A: Graph-based entity mapping with fuzzy matching (chosen)
### Option B: Rule-based mapping tables
### Option C: ML-based semantic embedding matching
### Option D: Manual mapping configuration UI

## Decision Outcome

**Chosen option: Graph-based entity mapping with fuzzy matching**.

The schema from each connected system is modelled as a directed graph where nodes are entities/fields and edges represent relationships (foreign keys, joins, references). Cross-system entity candidates are generated by multi-factor fuzzy matching; a second graph pass surfaces structural inconsistencies.

### Analysis Pipeline

```
1. Schema Ingestion
   ├── Call BaseConnector.introspect_schema() on each system
   └── Build EntityGraph per system (networkx.DiGraph)

2. Cross-System Entity Candidate Generation
   ├── Name similarity (RapidFuzz token-sort ratio) — weight: 0.35
   ├── Field set overlap (Jaccard similarity of field names) — weight: 0.30
   ├── Cardinality similarity (same order-of-magnitude row count) — weight: 0.15
   ├── Field type distribution similarity — weight: 0.10
   └── Semantic role detection (primary key, timestamp, currency) — weight: 0.10

3. Match Scoring and Filtering
   ├── Compute weighted composite score (0.0 – 1.0)
   ├── Apply configurable threshold (default: 0.65)
   └── Emit EntityMapping(confidence=score, evidence=[...])

4. Inconsistency Detection on Matched Pairs
   ├── Key type mismatch (integer vs. UUID vs. string)
   ├── Nullability difference (nullable in one, required in another)
   ├── Value format mismatch (date format, phone format, currency code)
   ├── Cardinality divergence (1:1 vs. 1:N relationship)
   └── Missing fields (field present in system A, absent in system B)

5. Impact Ranking
   ├── Affect score: how central is this entity to the proposed AI use case?
   ├── Breadth score: how many systems have conflicting representations?
   └── SchemaInconsistency(severity=HIGH|MEDIUM|LOW, impact_score=0-100)
```

### Graph Representation

```python
import networkx as nx

class EntityGraph:
    """Directed graph of entities and their relationships within one system."""
    graph: nx.DiGraph  # nodes: Entity, edges: Relationship
    system_id: str
    snapshot_at: datetime

class CrossSystemGraph:
    """Bipartite graph connecting matched entities across systems."""
    graph: nx.Graph  # bipartite; edge weight = match confidence
    entity_graphs: dict[str, EntityGraph]

    def community_clusters(self) -> list[list[Entity]]:
        """Return groups of entities that likely represent the same business concept."""
        return list(nx.community.louvain_communities(self.graph))
```

### Positive Consequences

- **Automated discovery**: the weighted scoring approach handles arbitrary naming conventions without manual configuration tables.
- **Confidence expression**: every `EntityMapping` carries a `confidence` score and an `evidence` list explaining the contributing factors.
- **Explainability**: graph structure and scoring weights are inspectable; architects can see exactly why two entities were matched.
- **Configurable thresholds**: `matching_threshold`, `field_weight_*` parameters are exposed in `config.yml`; no code changes required for tuning.
- **Network analysis**: `networkx` community detection identifies clusters of related entities across all systems, surfacing systemic inconsistency patterns.
- **Incremental re-analysis**: when a new system is connected, only its entity graph needs to be rebuilt; cross-system matching reuses cached graphs for unchanged systems.

### Negative Consequences

- Fuzzy matching produces false positives at scale; the default threshold (0.65) was calibrated on a test dataset and may need tuning for unusual naming conventions.
- Graph construction for very large schemas (1,000+ entities) can be memory-intensive; schemas are chunked and streamed for analysis.
- The confidence model requires explanation to non-technical buyers; the reporting layer must translate scores into natural-language rationale.

## Alternatives Considered

### Option B: Rule-Based Mapping Tables

Maintain a curated library of known equivalences: `salesforce.Account = sap.KNA1 = snowflake.dim_customer`.

| Criterion | Assessment |
|-----------|-----------|
| Accuracy | High for known mappings; zero coverage for unknown systems or custom entities |
| Automation | Requires manual curation; does not scale to customer-specific schemas |
| Maintenance | Library must be updated for every new enterprise system version |
| Verdict | **Rejected** — enterprise customers have extensively customised schemas; a rules library would have low recall for real-world deployments |

### Option C: ML-Based Semantic Embedding Matching

Embed entity/field names and descriptions using a sentence transformer; match by cosine similarity in embedding space.

| Criterion | Assessment |
|-----------|-----------|
| Accuracy | Potentially high for description-rich schemas; degrades when descriptions are absent |
| Enterprise applicability | Most enterprise system schemas (ERP especially) have terse, cryptic field names with no descriptions |
| Operational complexity | Requires embedding model inference at runtime; cold-start latency; model versioning |
| Explainability | Cosine similarity in embedding space is opaque to enterprise architects |
| Verdict | **Rejected as primary strategy** — embedding quality degrades on enterprise naming conventions; kept as a supplementary signal for future versions when field descriptions are available |

### Option D: Manual Mapping Configuration UI

Let users manually define entity and field equivalences through a configuration UI before running analysis.

| Criterion | Assessment |
|-----------|-----------|
| Accuracy | Perfectly accurate for what the user configures |
| Time to value | Configuration for a large enterprise schema takes days or weeks |
| Coverage | Only discovers inconsistencies in explicitly mapped entities |
| Product fit | Defeats the "fast turnaround" value proposition; shifts work back to the customer |
| Verdict | **Rejected as primary strategy** — acceptable as an *override* mechanism for low-confidence automated matches, not as the primary discovery mechanism |

---

## Implementation Notes

- Primary library: `networkx` (graph construction, community detection, shortest-path analysis).
- Fuzzy matching: `rapidfuzz` (Rust-backed; replaces `fuzzywuzzy` for performance at scale).
- Thresholds configurable in `config.yml` under `analysis.schema_matching.*`.
- Entity graphs are cached in Redis as serialised `SchemaSnapshot` models after initial introspection (see ADR-006).
- Analysis runs as a Celery task to avoid blocking the FastAPI event loop (see ADR-008).
